# Учёт моделей, расходов и времени

## Конфигурация итогового прогона

Для каждой модели указать точный `model_id`, назначение, карточку OpenRouter, провайдера или маршрут, входной и выходной тарифы в USD за миллион токенов. Учитываются диалог, извлечение параметров, проверка, генерация схем, модели поиска и эмбеддингов, включая подготовку индекса, и все резервные вызовы. Смена маршрута возможна среди заранее объявленных допустимых вариантов.

У каждого варианта входной тариф не выше $0,10 за миллион токенов. Проверяется максимум по конфигурации. Выходного порога нет, стоимость выхода учитывается полностью. Бесплатный маршрут должен явно присутствовать в каталоге с нулевой ценой. Личные кредиты, промокоды и скидки не меняют зачётный тариф. Организаторы фиксируют единый снимок каталога с датой и временем перед прогоном. При отдельном тарифе провайдера используется заявленный маршрут.

Другой API или локальный запуск допустимы при подтверждаемом соответствии модели каталогу и воспроизводимом подсчёте токенов по общему тарифному снимку. Фактический локальный платёж и оценочная стоимость — отдельные значения. Ограничения CPU-only и 8 ГБ VRAM для этого кейса не заданы. Допустимы программный расчёт, поиск по ключевым словам и генерация XML без отдельного модельного вызова. [Каталог](https://openrouter.ai/models) · [Учёт использования](https://openrouter.ai/docs/cookbook/administration/usage-accounting) · [Эмбеддинги](https://openrouter.ai/docs/api_reference/embeddings)

## Запись вызова и расчёт

- Идентификаторы `session_id`, `turn_id`, `call_id` и идентификатор ответа провайдера для API. Также `model_id`, маршрут, назначение, время начала и конца, статус.
- Исходный usage провайдера и нормализованные входные и выходные токены, источник сведений, кэш и reasoning при наличии. Записываются тарифы, оценочные суммы входа, выхода и всего, фактическая стоимость `usage.cost` при наличии. Секреты в журнал не попадают.
- Вход включает инструкции, историю, переданные документы, эмбеддинги и промежуточные операции. Входные токены, включая кэшированные, оцениваются по базовому входному тарифу. Для эмбеддингов без текстового выхода выходные токены равны нулю. Уже учтённые в выходе reasoning-токены повторно не складываются.
- Каждая попытка учитывается отдельно, включая сбои, отмены и повторы, если были начислены токены. Повторное получение usage одной попытки обновляет ту же запись `call_id`. При недостающих данных использовать статус `unknown` и сверить по данным провайдера. Оценка по числу символов не заменяет измерение.
- `C_call = (T_input × P_input + T_output × P_output) / 1 000 000`. Сессия суммирует вызовы всех моделей и всех шагов, включая правки. Контрольный пример: 10 000 входных по $0,10 и 2 000 выходных по $0,40 за миллион дают $0,0018.
- Однократную подготовку базы зафиксировать и показать отдельно. Эмбеддинги запроса, переиндексация во время диалога и другие действия по запросу входят в сессию. Повторная выдача готового результата приложением без вызова может иметь нулевой расход, если это подтверждает журнал.

После завершения сессии показать модели, числа вызовов и токенов по входу/выходу, суммы по входу, выходу и сессии. Фактический расход показывается отдельно при отличии. Использовать достаточную точность или отметку «< $0,000001». Отметить неподтверждённые данные. Выгружать связанные с сессией записи в JSON, JSONL или CSV и хранить их на время проверки.

## Время шага

Точка начала — отправка сообщения. Точка окончания — полностью доступный ответ и завершённый рендеринг изменившихся таблицы и схемы, когда они нужны. Для уточнения — отображение всех вопросов и вариантов ответа. Сеть, очередь, поиск, все внутренние вызовы и повторы, отрисовка и технические сбои входят в замер. Первый токен стрима не завершает шаг. Время ответа человека исключается.

Среднее по всем пользовательским шагам общего прогона должно быть ≤ 15 секунд. Допустимы предварительная загрузка приложения и однократная индексация открытой базы. Предварительное выполнение закрытых запросов исключено. Организаторы могут повторить весь затронутый прогон на одинаковых условиях при подтверждённом общем сбое провайдера. Неполный журнал либо превышение среднего лишают 2 баллов за скорость.

## Экономичность

Средняя цена команды — сумма оценочных расходов всех сессий общего прогона, делённая на одинаковое для всех число сценариев. Берутся полные журналы со всеми попытками. Допуск требует подходящих моделей, проверяемого учёта и завершения всех обязательных сценариев ожидаемым типом ответа, включая корректное уточнение или предварительный результат для принципиально неполного сценария. Пустой ответ, ошибка и общий отказ на поддерживаемом сценарии завершением не считаются.

При разных ценах среди допущенных команд балл команды равен `ceil(10 × (C_max − C_i) / (C_max − C_min))` в пределах 0–10. Цены $0,001, $0,002 и $0,004 дают 10, 7 и 0. Округляется итоговый балл, вычисление ведётся по точным расходам. При равенстве цен или единственной допущенной команде каждый допущенный получает 10. Остальные получают 0 и не участвуют в определении границ.


## Сверка поздно полученного usage — задача 08

Локальный оператор может дополнить существующую попытку данными из отчёта
провайдера. Новая попытка, сообщение или модельный запрос не создаются.
Команда по умолчанию проверяет файл без записи. Она работает с настроенной
БД, поэтому используется оператором на выбранном окружении; публичного
endpoint для самостоятельной подстановки токенов пользователем нет.

```sh
uv run --project backend --locked python -m partner_agent.runtime.usage_reconciliation --input /private/provider-usage.json
uv run --project backend --locked python -m partner_agent.runtime.usage_reconciliation --input /private/provider-usage.json --apply
```

Пример структуры (идентификаторы заменить значениями из журнала):

```json
{
  "schema_version": 1,
  "source": "provider_export",
  "calls": [
    {
      "call_id": "00000000-0000-0000-0000-000000000001",
      "response_id": "resp-synthetic",
      "model_id": "synthetic/model",
      "provider": "synthetic/route",
      "usage": {"input_tokens": 10000, "output_tokens": 2000, "cost": 0.002}
    }
  ]
}
```

Оператор сначала сверяет отчёт с источником провайдера. Импорт не проверяет
подлинность самого файла и не доказывает идентичность модели шлюза. В выгрузке
источник таких сведений явно `operator_provider_export`, а не автоматическое
получение через API. Нужны точные совпадения call_id, response_id, настроенной
модели и варианта провайдера. Если response_id не был получен, попытка остаётся
неизвестной до отдельного разбора; по времени/позиции в списке она не угадывается.

Дополняются только недостающие значения. Конфликт с известными токенами,
стоимостью или числовыми деталями отклоняет весь пакет. Активную попытку
изменять нельзя. Число попыток, статус ошибки/отмены, тарифы и время вызова
не меняются. Эксплуатационный дневной резерв тоже не переписывается:
это ретроспективная сверка сессионного журнала. Повтор тех же значений
идемпотентен, даже если изменилось
оформление входного файла. JSON с повторными ключами или call_id, неизвестными
полями верхнего уровня, некорректными числами и пакет >1 МиБ отклоняется.
В пакете не более 1000 записей, объединённая числовая проекция usage ограничена
64 КиБ. Неизвестный расход не заменяется нулём.

Сохраняются SHA-256 входного файла, дата импорта и история предыдущих
подтверждений (до 20 изменяющих импортов на попытку; затем нужен отдельный
разбор). Сам частный отчёт оператор хранит отдельно. В БД остаётся числовая
проекция raw usage без произвольных текстов, credentials или ответов модели.
После применения владелец обновляет панель расходов/JSON-выгрузку: суммы
пересчитываются из тех же call_id; доступ чужого администратора не расширяется.

Контрольный сценарий: две HTTP-попытки одного шага, первая 429 с неполным
usage, вторая с 10 000 входных/2000 выходных токенов. До сверки итог неизвестен,
известная часть $0,0018. После дополнения первой попытки итог $0,0036,
фактический расход API отдельно $0,004; вызовов по-прежнему два. Следующий
шаг без вызова модели увеличивает число пользовательских шагов, сохраняя
число вызовов. Полные замеры обоих шагов входят в среднее, без приравнивания
времени первого токена к полному ответу.

Текущий поиск/подготовка корпуса используют локальный BM25 и не подключают
модель эмбеддингов. Импорт usage не добавляет такую модель и не создаёт
выдуманные индексные вызовы. При её будущем подключении понадобится отдельный
учёт подготовки и запросов. Настоящий общий прогон, сверка с биллингом и
среднее ≤15 секунд остаются отдельной задачей 12 с согласованным бюджетом.
