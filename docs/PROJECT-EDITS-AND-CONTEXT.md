# Адресные правки и контекст большого проекта

Два связанных P0: повторная генерация всего Requirements v3 для малой правки
и ограничение сериализованного контекста 32000 символов.

## Контракт изменения

Сохранённый v3 редактируется через design_patch.operations: add/update/remove,
коллекция и точный ID сущности, values только изменённых полей. Отдельный update
для project допускает только поля инженерных условий и заметок. До 64 операций;
новый проект по-прежнему извлекается целиком. Старые полные предложения совместимы.

База берётся из захваченного сервером RunDesignContext, не из ответа модели.
Патч применяется к копии атомарно; полная Requirements19 проверяет ссылки,
сети и типы. Существующий путь завершения проверяет владельца и актуальность
ревизии, назначает provenance и ID новых объектов, пересчитывает артефакты.
Модель не может менять ID, импортные метаданные, sources и схему документа.
Удаление используемого объекта без согласованных изменений ссылок отклоняется.

## Контекст

Модели передаётся компактный вид Requirements19 без значений по умолчанию,
provenance и неизменяемых импортных метаданных. Полная база остаётся на сервере.
Значимые различия checks=null/[] сохраняются. Из истории удаляются повторные
целые пары; текущий запрос сохраняется дословно. Поля проекта не обрезаются.

Для объявленного окна модели учитывается резерв выхода и консервативная
оценка UTF-8 bytes + 64 на сообщение. Абсолютный предел 256000 UTF-8 байт (с запасом на сообщения)
ограничивает расход/размер и остаётся ниже порога тарифного повышения272k; при неизвестном окне остаётся прежний 32000.
Увеличение предела дополняет сокращение дублей, не заменяет его. Если полный
компактный проект не помещается, вызов модели не совершается.

## Проверки

Регрессии патча и контекста проверяются отдельно. Сквозное сохранение,
пересчёт, архив и конфликт ревизии проверяются на отдельной PostgreSQL.
Проверены добавление/переименование/удаление, атомарность ошибочного пакета,
запрет перезаписи конкурентной ручной версии, сохранность старого draw.io.
Ранняя схема и пакетные уточнения уже в PR27/21/31. На свежей develop
браузер подтвердил «Сохранить и рассчитать»: версия2, одно правило, SVG,
повторное открытие после reload. Платных вызовов для этой проверки не было.

Отдельные регрессии: компактный проект из242систем помещается в прежние
32000 без потери сущностей; более длинный проект использует объявленное окно.
Дубли истории убираются целыми парами. При большом расчёте сохраняются
числа, фактическое размещение и все связи правил с потоками, вместо повторения
полных подробностей каждого правила. Запрос вне окна не доходит до провайдера.
Живой шестишаговый сценарий выполняется после этих изменений.
Текущий статус проверок фиксируется в progress.md и PR.

Пустые nullable name/purpose/policy/details/existing_firewall_name модели
нормализуются в null. Это отсутствие значения, не выдумывание данных.
ID, ссылки, протоколы, числа и обязательные пояснения остаются строгими.
Проверено отдельно для нового полного документа и адресной операции.

## Ускорение: замеры и следующий план (предложение)

По шести живым ходам API-вызов занимает в среднем17.181с, серверный шаг20.889с,
полный показ21.583с. Разница сервер/API≈3.707с не локализована по стадиям;
нельзя целиком приписывать её поиску или очереди. Разница UI/сервер≈0.694с.
TTFT отдельно не измерен, поэтому ожидание провайдера и генерация не разделены.
Снижение задержки интерфейса само по себе не решит цель15с.

1. Замерить стадии: очередь/claim, контекст/ACL/поиск, API до первого токена,
   генерация, транзакции/расчёт/артефакты и показ. Убрать повторную работу,
   сохраняя все проверки доступа и пересчёт только изменённого проекта.
2. Разделить инструкции для создания, адресной правки и справки. Не передавать
   полный контракт редактирования справочному запросу. Стабильный префикс
   оставлять неизменным; prompt-cache попадания/фактическую поддержку шлюза
   проверить, а не считать гарантированными.
3. Заготовки — схемы структуры и серверного пояснения из рассчитанного результата.
   При проектировании не генерировать пространный answer, если его заменяет
   серверное объяснение. Извлекать факты/изменения, остальные поля достраивать
   по контрактным defaults; неизвестное не превращать в известное. Первичное
   создание дало1157выходных токенов, адресная правка284; это разные задачи,
   не контролируемый эксперимент и не доказательство одинакового ускорения.
4. Кэшировать только пригодный к повторному использованию проверенный результат
   с учётом вопроса/контекста, режима, ревизии, версий документов, ACL и модели.
   Отзыв доступа/обновление источника запрещает повторную выдачу. Похожесть слов
   не должна смешивать отрицание, направления и требования проекта.
5. Проверенные тематические карточки ICAP/Тамбур/протоколы могут дать короткий
   контекст с исходными ссылками; это не заготовленные ответы на benchmark.
   Неопределённый/смешанный вопрос сохраняет обычный поиск и контекст диалога.

Настоящий streaming может раньше показать разрешённый текст, но не доказывает
сокращение полного времени. Непроверенный проект/JSON публиковать нельзя.
Flex у первичного провайдера обменивает стоимость на повышенную задержку;
вклад Polza/маршрута у нас отдельно не установлен. Сравнение маршрутов —
отдельный эксперимент с тарифом/бюджетом, автоматическую смену не выполнять.

Предложения пока не реализованы. Новых платных вызовов в этом анализе нет.
Ожидаемое ускорение и сохранение качества нужно подтвердить повтором сценариев,
а не обещать произвольное время ответа.

Первичные источники:
- [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization).
- [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).
- [Flex processing](https://developers.openai.com/api/docs/guides/flex-processing).

## Составная правка и невидимое устройство — 22 ноября

Проверка конкретного сообщения владельца выявила частичный результат: новая
система сохранена, но нового TCP-потока в ревизии нет. Старый UDP-поток
остался неизменным. Сырой ответ не хранится, поэтому конкретное рассуждение
модели не установлено. Отдельный дефект layout: при наличии рассчитанных правил
он рисовал только их участников; добавленное устройство исчезало из вида.

Исправления: инструкция требует учесть все части составного запроса и сохранять
неполный новый поток с явно неизвестными полями, а не терять намерение связи.
Повтор запроса должен использовать существующее устройство по ID.
Сервер формирует квитанцию из фактической разницы сохранённых условий:
добавленные/изменённые/удалённые устройства и потоки. Если новый узел не связан,
а потоки не изменены, ответ прямо сообщает, что новый обмен не сохранён.
Это не независимое доказательство выполнения всех намерений пользователя;
защита не подменяет неизвестное направление догадкой.

Layout показывает известные устройства с назначенной сетью даже без рассчитанного
обмена. Неподтверждённых стрелок нет. До16карточек на сторону; переполнение
попадает на дополнительные листы без потери устройств. Палитра/МЭ/узлы/ядро
сохранены. Ранее сохранённые артефакты не перерисовываются: новое отображение
применяется к новым ревизиям. Известный протокол больше не переспрашивается
одним общим вопросом о протоколе и ответных пакетах.

Локально:641unit,35PostgreSQL,Ruff/mypy99 прошли. Проверяются частичная
правка, незаданный режим TCP, неизменность UDP и наличие нового узла без
выдуманных связей. Два живых шага на отдельном тестовом проекте запланированы
в остатке ранее согласованного бюджета5RUB; исходный проект владельца не меняется.
