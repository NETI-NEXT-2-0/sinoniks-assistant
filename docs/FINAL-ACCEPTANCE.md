# Итоговая приёмка — задача 12

Сейчас готовится комплект доказательств. Живой модельный прогон не выполнен,
баллы и качество реальной модели не подтверждены. Технические проверки
перечислены в [общей приёмке](ACCEPTANCE.md) и профильных отчётах.
Живой маршрут и бюджет будут зафиксированы после получения конфигурации
от владельца. Qwen ниже приведён как расчётный пример; платный этап отложен.
Демонстрация `localhost:8080` закреплена на прежнем образе; подготовка и
приёмка используют другие исходники, контейнеры и тестовую БД.

## Единый кандидат и план

Перед прогоном выбрать неизменяемый полный Git SHA, проверить его и собрать
отдельный образ из чистого снимка этого SHA. Записать SHA, image ID, дату,
контрольные суммы корпуса и тарифного снимка. `runtime_git_sha` в комплекте
подтверждает оператор: сборщик не умеет доказывать, из какого кода запущен
сервер. После исправления кода нужен новый кандидат и новый комплект,
прежние результаты не перезаписываются.

Имеется **16 сценариев и 17 независимых сессий**. U04 разделяется на три сети
и две открытые сети. Это уточнение количества сессий, не увеличение сметы:

| Сессия | План модельных попыток |
| --- | ---: |
| F01, F02, F04, F07 | По 1 |
| N01, N05 | По 4 |
| O01 | 3 |
| Q01, Q10 | По 1 |
| U01 | 2 |
| U02-separate, U02-shared | По 3 |
| U03 | 7 |
| U04-three, U04-open | 1 и 2 |
| U05 | 1 |
| U06 | 4 |

Всего запланировано 40, общий потолок — 60 попыток вместе с резервом,
ошибками, повторами и дополнительными проверками. Программный ответ может
не вызывать модель. Использовать новые сессии для разных случаев; внутри
N05, U03 и других продолжений сохранять исходную сессию. Не вводить ожидаемые
ответы эталона в запрос модели. F04 с неуточнённым «SMB, автоматически»
требует вопроса о PULL/PUSH и ручной оценки неоднозначного эталона.

## Подготовка без внешних запросов

[Публичный пример маршрутов](examples/acceptance-routes.json) копирует
подготовительный снимок из [учёта](ACCOUNTING.md#маршруты-для-приёмки).
Перед настоящим прогоном сверить его с согласованным снимком организаторов.
В конфигурации нет ключей. Не добавлять их в этот JSON или Git.

```powershell
$candidateSha = git rev-parse HEAD
uv run --project backend --locked python -m partner_agent.acceptance_bundle prepare --git-sha $candidateSha --config docs/examples/acceptance-routes.json --output .local/acceptance-candidate
```

Можно дополнительно передать `--benchmark /private/04_benchmarks.json`.
Тогда `inputs.json` содержит только девять `query` и явный `follow_up.user_answer`
для N05. Поля `expected`, `expected_answer`, `explanation`, `must_ask` и другие
подсказки не копируются; исходник остаётся прежним. Хеш входного пакета
фиксируется в плане и проверяется при сборке отчёта. Если пользовательский
текст отсутствует, инструмент отказывает, не извлекая его из ожидаемого ответа.
Уточнение N05 подавать после соответствующего вопроса модели; отсутствие
нужного вопроса фиксировать как недостаток даже при правильном финальном числе.

Создаются `plan.json` и `captures.json`. Второй содержит пустые поля для
17 сессий. Сборщик не читает окружение, не делает сетевых запросов, не
запускает контейнеры или модель. `budget_approved: false` не является
разрешением на расходы. Существующий каталог не перезаписывается.
Расчёт по данному снимку — до **$1,47** за максимум 60 попыток, но платный
запуск отдельно согласовывается по AGENTS.md. Ключ для отдельного окружения
хранится локально, например в `.local/acceptance.env`; демонстрационный `.env`
не меняется. Дневной и разовый лимиты, фиксированный маршрут без автоматического
резерва и учёт включаются по ACCOUNTING.md. Изменение условий требует новой сметы.

В текущем техническом срезе прошли26 целевых проверок сборщика и полный
`./init.sh check`:556 backend/18 frontend, Ruff/mypy95/TS/build.
Свежий публичный[список маршрутов](https://openrouter.ai/api/v1/models/qwen/qwen3-30b-a3b-instruct-2507/endpoints)
подтвердил объявленные тарифы и контекст; этот GET не вызывал модель и не
заменяет согласованный тарифный снимок организаторов.

## Что сохранять в каждой сессии

1. Итоговый снимок чата `/api/v1/chats/{id}/snapshot`: весь ход вопросов,
   отказов, уточнений и созданных ревизий. Если диалог длиннее страницы,
   дополнительно сохранить сообщения предыдущих страниц.
2. Журнал `/api/v1/chats/{id}/accounting/export`. В него входят все попытки,
   в том числе ошибки, отмены и неизвестный usage. Прямые ответы остаются
   пользовательскими шагами. Все замеры должны относиться к полному ответу,
   диаграмме и цитатам, а не только к первому токену или карточке.
3. Для проектных сценариев — экспертный JSON, актуальный draw.io и исходные
   требования. В N01 и U04-open предварительная схема может быть недоступна;
   это не повод выдумывать известные условия.
4. Для N05 сохранить начальный и уточнённый JSON; для U03 — четыре допустимые
   ревизии и их схемы. Не подменять начальный файл финальным. Эти дополнительные
   версии пока прикладываются рядом вручную и проверяются отдельным аудитом.
5. Для O01 — выгрузку пожеланий; для Q/O — раскрытые цитаты с именем файла и
   разделом, доступ к фрагменту и отдельный доступ к оригиналу. Для U05 —
   исходный и изменённый/reopened draw.io. Скриншоты привязываются к шагам.
   Сборщик проверяет доступность и хеш PNG. Содержание кадра оценивает эксперт.

Все сырые ответы, исходники, снимки чатов и расходы хранить в приватном
каталоге вне Git. В `captures.json` указать относительные пути к четырём
основным артефактам, UUID сессии, подтверждённый runtime SHA и ручной статус
`not_checked`, `pass` или `fail`. Отсутствующие поля оставить `null`.
Для каждого шага в `steps` указать `step_id`, `turn_id` из журнала,
`revision` (номер показанной ревизии или `null`), `prompt`, `expected`,
`observed`, ручной `review_status` и `screenshots` (относительные пути PNG).
Сборщик связывает шаг с полным временем и идентификаторами вызовов в журнале.
Исходный кадр ошибки сохранять до повтора. В отчёте
`automatic_evidence_status` и `expert_review_status` имеют отдельные значения.
Для дополнительных независимых журналов допустим `case_id: EXTRA-...`;
их расходы и попытки тоже включаются. Комплект отражает только переданные
журналы и не доказывает полноту расходов всего аккаунта провайдера.

```powershell
uv run --project backend --locked python -m partner_agent.acceptance_bundle collect --plan .local/acceptance-candidate/plan.json --captures .local/acceptance-candidate/captures.json --output .local/acceptance-candidate/inventory-01.json
```

Сборщик проверяет относительные пути, хеширует файлы, сопоставляет сессии,
находит повторные session/call/turn IDs, неизвестные расходы, несогласованный
тариф/маршрут/снимок, незавершённые вызовы, отсутствие полного таймера и превышение
лимитов. Стоимость пересчитывается по токенам и объявленным тарифам. Кэш и
reasoning не добавляются повторно. Карточный таймер не заменяет полный.
Модель, названная в конфигурации, не считается криптографически подтверждённой.
Фактический биллинг сверяется отдельно.

Код возврата 1 означает неполный комплект, 2 — некорректный ввод. Код 0 означает
только готовность переданных материалов к рассмотрению. Даже при нём
`acceptance_complete` и `model_quality_automatically_graded` остаются `false`.
Сборщик не ставит баллы и не проверяет смысл ответа, оптимальность правил или
визуальное качество. Среднее 15 000 мс включительно проверяется только при
наличии всех полных замеров; иначе итог неизвестен.

Последний офлайн-инкремент с пакетом входов проверен:561 backend/
18 frontend, Ruff/mypy95/TS/build;31 целевая проверка, без сетевых вызовов.
Отдельный образ e127010 собран из чистого Git-архива и использован для
браузерной проверки источника на320/390/1440 px. Это предварительный
контейнерный срез; общий live-кандидат выбирается после получения конфига.

## Отдельные содержательные проверки

- Сверить девять открытых эталонов через `partner_agent.benchmark_audit`
  с приватным benchmark и файлами `F02.json`, `N05.json`, `N05-follow-up.json`
  и т. п. Этот аудит отдельно оставляет неоднозначные условия на ручной проверке.
- Проверить все применимые подкритерии [таблицы оценивания](ACCEPTANCE.md#оценка):
  архитектуру и направления, минимум правил, предварительные результаты,
  понятность уточнений, цитаты, редактируемость схем, пользователей и пожелания.
- Проверить устойчивость на попытке отменить ограничения кейса и на инструкции
  внутри недоверенного документа. Отказ не должен менять корректный проект.
- Пройти UI на широком/узком экране, открыть и изменить draw.io, вернуть
  исправленный проект и сравнить выгрузки. Проверить восстановление и права.
- Пересчитать общий журнал, число попыток и тарифы, сверить фактический биллинг.
  Неизвестное не записывать как нулевой расход или успешную проверку.

Перед выпуском в main также нужны обязательные CI/контейнерный/браузерный/
конверсионный/восстановительный сценарии по AGENTS.md. Подготовка этого комплекта
не создаёт release/tag и не подтверждает прохождение итоговой приёмки.
