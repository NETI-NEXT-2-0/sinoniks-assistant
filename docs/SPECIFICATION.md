# Требования к продукту

## Объём и результат

Русскоязычный веб-продукт для инженера заказчика, специалиста по информационной безопасности и инженера внедрения. Вход — свободное описание инфраструктуры и обмена. Рамки проекта — две сети, одна граница, один «Синоникс» версии 1.9 и конкретные системы в каждой сети. Отказоустойчивость, резервирование и обмен между тремя и более сетями выходят за обязательный объём. Для нескольких сетей предложить выбрать пару. Доступ ко всей подсети выходит за рамки этого способа обмена. Приложение выполняет предварительное проектирование, конфигурацию физического оборудования и инфраструктурные команды выполняют за его пределами.

Завершённый проект включает объяснение размещения и ограничений, минимальный набор правил с обоснованием, [диаграмму и редактируемый экспорт](DIAGRAMS.md), JSON для эксперта и [сумму расходов](ACCOUNTING.md). Консультация о продукте завершается ответом с проверяемыми источниками. При запросе неподдерживаемой функции объяснить предел, предложить возможную альтернативу и сохранить применимую часть проекта.

## Диалог и ревизии

Из сообщения извлекаются сети и их типы, системы, данные и файлы, направления, режимы, протоколы и известные порты. Уточнять только параметры, меняющие решение. Для потоков данных это сторона, обратная передача, протокол, порт и получатели. Для файлов — отправка и получение на каждой стороне, способы и протоколы, проверки, разделение видимости, число пользователей. Можно группировать связанные вопросы. Варианты «не знаю» и «другое» со свободным вводом доступны в каждом вопросе. Введённые значения сохраняются в контексте. Исправление пользователя заменяет предыдущий факт.

Неизвестные IP, протоколы, порты, направления, проверки и количества остаются неизвестными. Когда можно вывести нижнюю границу, показать «Предварительная оценка: минимум N правил», список пробелов и допущения. Если корректной нижней оценки пока нет, продолжить уточнение. При двух открытых сетях спросить, какую сторону считать защищаемой, и записать согласие как проектное допущение. Без согласия результат предварительный. Исходное описание остаётся доступным.

Диалог продолжается после выдачи результата. Вопрос о схеме использует текущую конфигурацию без новой ревизии. Однозначная допустимая правка создаёт актуальную ревизию с согласованными пояснениями, правилами, схемой, JSON и файлом. Для неоднозначной правки сначала выбрать объект вместе с пользователем. Если правка невозможна, объяснить ограничение и сохранить последнюю корректную ревизию. Повторное открытие диалога и скачивание используют актуальную ревизию. «Новая сессия» создаёт независимый контекст и счётчик расходов.

## Размещение

Цепочка для типового случая — открытая сеть → межсетевой экран → «Синоникс» внутри защищаемого сегмента → конкретные системы закрытой сети. Узел А обращён к МЭ и открытой стороне, Узел В — к закрытой, Ядро находится между узлами. Имеющийся подходящий МЭ используется повторно. Если пользователь просит поставить устройство снаружи, объяснить рекомендуемое размещение. Для двух открытых сетей методология допускает МЭ с обеих сторон с обоснованием. USB подключается непосредственно к Узлу А и минует МЭ. При загрузке с USB файлы направляются в закрытый сегмент, при выгрузке источник находится в закрытом сегменте.

МЭ обеспечивает базовую защиту и проверку обычного TCP/UDP в пределах своих возможностей. «Синоникс» разрешает только согласованный обмен между системами, может ограничивать адреса отправителей, фильтрует поддерживаемые промышленные протоколы по структуре и проверяет файлы. Несогласованные правила администраторов сторон передачи не обеспечивают. В расчёте фигурируют логические правила «Синоникса». Предел одного ПАК — 256, при превышении показать ограничение и рассчитанную потребность без обрезки результата.

## Правила данных

| Случай | Правила |
| --- | --- |
| Несколько отправителей, один получатель, одинаковые протокол, порт и режим | Одно. Отправители обращаются к узлу в режиме collect, второй узел доставляет получателю в режиме exchange. |
| Разные получатели, порты или протоколы | Отдельное правило на каждую несовместимую комбинацию. |
| Запрос и ответ по одному соединению | Одно двунаправленное правило со стороной инициатора. |
| Журналы, резервные копии и телеметрия по TCP/UDP без обратного обмена | Однонаправленный режим, обратные пакеты запрещены. Наличие обратного обмена уточняется при необходимости. |
| MQTT, Modbus TCP, МЭК 104 | Только двунаправленный режим. Политики ограничивают разрешённые топики, регистры, типы данных и команды в рамках соответствующего протокола. |
| NTP в закрытый сегмент | Одно однонаправленное правило от сервера времени независимо от числа устройств, для которых нужна синхронизация. |

Каждое правило указывает тип, стороны, режим, протокол, порт при наличии и причину его выделения либо объединения.

## Правила файлов

- Одно правило может передавать файлы в одну или обе стороны при единых проверках и общей видимости для группы. Проверки Узла А и Узла В могут отличаться в одном правиле. Разные профили на одной стороне либо изолированные группы доступа требуют раздельных правил.
- На одном узле для одного правила может быть одна автоматическая настройка. PULL забирает файл из хранилища на отправляющей стороне. PUSH доставляет поступивший файл в хранилище. Каждый PULL или PUSH закреплён за своим правилом. Два PULL на противоположных узлах либо PULL и PUSH на одном узле требуют разделения. Автоматический двусторонний обмен двух хранилищ по расписанию требует двух правил.
- Ручной метод использует SFTP, автоматические PULL/PUSH поддерживают SFTP, FTP и SMB, USB доступен на А. Методы и протоколы двух сторон можно сочетать. Человек с разрешённым USB может использовать то же правило вручную при совместимых проверках и доступе.
- Проверки включают маску имени, тип или расширение, размер, целостность по цифровой подписи, внешние антивирус, песочницу и DLP по ICAP. Файл, не прошедший отправляющую проверку, не пересекает границу. Антивирус обеспечивается внешним сервисом. Запись действий конкретного человека относится к PAM.
- Для бонусного учёта каждый идентифицированный человек, вручную помещающий или забирающий файлы, учитывается один раз. Каждое PULL-правило требует одного технического пользователя, PUSH дополнительных пользователей не требует. Отобразить точное число, диапазон или явное неизвестное. Число пользователей само по себе не определяет число правил.

## Сведения о продукте и пожелания

Ответы о возможностях подтверждаются материалами кейса, с именем файла и разделом или страницей рядом с утверждением. При отсутствии основания сообщить, что сведений недостаточно. Версия 1.9 имеет приоритет перед общими презентациями. В частности, 256 правил и до 1 Гбит/с относятся к ПАК в рамках кейса, а не к веб-приложению. Проверять отдельно независимое администрирование сторон, аппаратные и программный ключи остановки обмена, локальный журнал и передачу событий SIEM/CEF, лицензирование файловых пользователей, ICAP и протоколы. Для Q01/Q10 старые имена источников в эталоне сопоставляются с актуальными файлами справочника и методологии.

Пожелания к возможностям и ответы «другое» сохраняются со связью с сессией и первоначальным смыслом. Экспертная выгрузка включает `requests_for_vendor`. Применимые требования пользователя сохраняются в конфигурации.

## Служебный JSON

| Поля | Что проверить |
| --- | --- |
| `schema_version`, `session_id`, `status` | Состояния `needs_clarification`, `preliminary`, `completed`, `unsupported`. Предварительный результат имеет собственный статус. |
| `networks`, `devices`, `firewall`, `synonyx` | Сети содержат идентификатор, имя и доверие. Системы ссылаются на сеть. Экран имеет сторону, у устройства есть место размещения и ориентация А/В. |
| `rules`, `rules_count` | `rules_count` равен длине списка. У правила есть `id`, `type`, `from`, `to`, `mode`, `protocol`, `port`, `description`. `from`/`to` ссылаются на сети, у двунаправленного `from` — инициатор. Неизвестный порт — `null`. Для файлов протокол и метод описывают обе стороны, проверки сторон выражаются в `checks_by_node`. |
| `unknowns`, `assumptions`, `sources` | Сохраняются реальные пробелы, согласованные допущения и подтверждающие материалы с локатором. |
| `file_users_count`, `file_users_range` | Точное число — целое, без файлов — 0, при диапазоне число `null`, диапазон `min`/`max`. Открытая верхняя граница — `max: null`. Для полностью неизвестного числа явно сохранить неопределённость. |
| `requests_for_vendor`, `usage`, `timing` | Пожелания, действующий накопленный учёт и замеры. |

Исходная структура приведена в `result.example.json`. На проверке важны смысл и согласованность представлений. Нумерация внутренних идентификаторов и порядок ключей свободны.
