Добавлена явная настройка `PARTNER_MODEL_REASONING_EFFORT` с вариантами low,
medium и high. Пустое значение сохраняет прежнее поведение провайдера.
Chat Completions и Responses получают параметр в своих форматах; настройка

Это гипотеза исправления задержки/обрезания, не доказательство качества:
результаты повторной живой проверки будут добавлены ниже.

Повтор на low/6000: F04 сохранил предварительную версию (32.203 с),
F07 вернул полный JSON, но отклонён валидатором (54.506 с). Ускорение не

вместо `/flows/<index>/…`. Добавлено преобразование только однозначного ID
существующей сущности при совпадающем target_id. Значения, смысл unknown и

Регрессии проверяют эквивалентность, идемпотентность и сохранение отказов для

значении. Живой повтор после этого исправления ещё требуется.

## Автоматические проверки и артефакты

Исходный кандидат: 676 unit и 260 PostgreSQL (без storage/parser), Ruff прошли.
Живые действия выполняются через настоящий браузер; фиксируется POST полного
рендеринга, не первый токен. Сохраняются исходные снимки чата, журнал,
экспертный JSON, draw.io и кадры. Файлы с учётками и сырые диагностические
ответы модели остаются закрытыми и в Git не включаются.

Для презентации готовятся отдельные кадры документов, редактирования копии,
подсветки чувствительных данных, пространств/групп и сравнения обычного читателя
с учеником. На испытательном стенде общее демо-чтение выключено; у двух обычных
аккаунтов различаются только разрешённые материалы. Это реальная проверка ACL,
а не разные ответы, заданные ролям в промпте. Основной сайт сохраняет общий
доступ для презентации, разрешённый владельцем ранее.

## Исправление ручной проверки PDF

На технической презентации из ZIP воспроизведён тупик публикации:
`native_text_order_uncertain` блокировал даже вручную исправленную копию.
Теперь куратор может отдельно подтвердить сверку порядка и смысла с оригиналом.
Подтверждение действует только для проверенной текстовой копии, входит в её
хеш и записывается в аудит; изменение текста сбрасывает флажок в интерфейсе.
Согласование исходных блоков без копии, неявное подтверждение, повреждённый
canonical и несвязанные сноски по-прежнему запрещены. Оригинал и его координаты
не изменяются. Цитаты из копии ссылаются на её символы, а не на выдуманную страницу.

Живая проверка исправления: техническая презентация (22 страницы) распознана,
копия сверена и очищена от шума схем, подтверждена и опубликована. Доступ на
ответ и целый оригинал выдан двум демонстрационным читателям. Проверки
исправленной копии на PostgreSQL/Garage/Qdrant: 6 passed, включая сохранность
оригинала, проверку SHA, ACL и подмену артефакта. Первый запуск storage-тестов
с техническим `storage.invalid` не являлся проверкой хранения; после настройки
реального тестового S3 повтор завершился успешно.

## Адресная правка файлового обмена

В U02 повторный ответ модели использовал `actors` вместо `actor_ids` на стороне
файлового обмена. Добавлен узкий разбор этого написания: только массив строк

Нормализация адресов примечаний также применяется до проверки адресного патча.
56 профильных регрессий прошли. Ошибка исходной попытки сохранена в журнале.

## Завершение ответа в интерфейсе

Повтор U02 сохранил правильную ревизию, но полный браузерный замер не завершился
за 330.574 с. В БД `message.completed` и `run.succeeded` присутствуют с разницей
5 мс; модельный шаг завершён примерно за 18 с. Причина в клиенте: selectChat
отменял запланированный refresh, оставляя ненулевой ref таймера. Последующие
терминальные события считали обновление уже назначенным. Ref теперь очищается
вместе с таймером. Неудачный шаг остаётся в журнале; неполный замер не заменяется
серверным временем или нулём. Требуется повтор на новой клиентской сборке.

Также устранён скрытый пробел формы: checks=null теперь всегда имеет вопрос
о проверках соответствующей стороны. Наличие известного профиля на соседнем
узле не скрывает вопрос и не подставляет его автоматически.

На следующем повторе модель вернула пустой пакет операций: условия уже были
сохранены. Раньше min_length=1 превращал этот ответ в `provider_invalid_design`.
Пустой пакет теперь не создаёт ревизию: сервер сообщает об отсутствии изменений
и показывает сохранённое пояснение захваченной версии, без повторного расчёта
новым решателем. Текст модели с заявлениями
о неподтверждённых правках не используется. В outcome записываются
`project_changed=false`, `task_completed=false`; это не считается применённой
правкой. Новый проект или пакет с неизвестными ключами по-прежнему не принимается.
Для больших проектов пояснение пустого пакета ограничено по объёму с явным
указанием на полный сохранённый расчёт. Регрессия с архивом на 128 правил
проверяет ограничение сообщения; отдельная проверка сохраняет историческое
число пользователей без переоценки текущим решателем.

## Дополнительный режим для последующей проверки скорости

Ни low, ни увеличение выхода сами по себе не подтвердили среднее ≤15 с.
Повтор low остановлен между шагами после 19 завершённых ходов: кодов ошибок и
браузерных исключений нет, среднее полное время 17.503 с. Это неполный прогон,
а не окончательная приёмка. Все попытки и их расходы сохранены.
В конфигурацию добавлен явный `none`; по умолчанию он не включается.
Передача `none` и отсутствие параметра проверяются
раздельно для обоих wire API и журнала. Возможность документирована в
[карточке GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).
До сравнительной живой проверки ускорение и сохранение качества не заявляются.

Первый сравнительный запрос с `none` всё равно вернул 1034 reasoning-токена.
Причина подтверждена [документацией Polza](https://polza.ai/docs/osobennosti/reasoning-tokens.md):
верхнеуровневый `reasoning_effort` игнорируется без ошибки; унифицированный API
читает `reasoning.effort`. Для точных хостов polza.ai/api.polza.ai формат исправлен,
для остальных OpenAI-compatible endpoint сохранён стандартный контракт.
Таким образом, предыдущие low/none — запрошенные, а не подтверждённые режимы.
Все их результаты сохраняются; новое сравнение проводится отдельно.

С исправленным wire-форматом (`583a456`) четыре сравнительных запроса завершены:
F01 — 7.635 с / 1 правило, F02 — 8.523 с / 3, F04 — 9.560 с / 1,
F07 — 9.526 с / 3; среднее 8.811 с, reasoning_tokens=0 на каждом.
Файловых пользователей F04/F07 — по одному; отсутствующие условия оставлены
предварительными. Это сравнение, а не доказательство полного прохождения.

Следующий полный повтор остановлен на третьем шаге F04: модель одновременно
заполнила проверки и пометила их `missing`. Сохранены исходный неуспешный ход,
его время 9.548 с и usage. Вход модели теперь удаляет только избыточные
`missing`-пометки у уже заданного значения с корректным путём и владельцем.
Значения полей не меняются. `user_unknown`, ошибочный владелец/путь и лишние
поля по-прежнему отклоняются строгим контрактом; импорт/редактор не ослаблены.

На повторе `f00ace4` выявлен содержательный провал без технического кода:
F01 дал справочный текст без проекта, F02 — уточнение без извлечения известных
потоков. Последовательность остановлена; эти шаги не считаются успешными.
Первичный перечень режимов в инструкции описывал только разговор/справку/отказ,
а проектирование добавлялось значительно позже. Приоритет проектного запроса
перенесён в начало: текст и цитаты не заменяют структурированные условия.
Проверочный стенд отдельно контролирует наличие проекта и число правил,
а не только отсутствие технических ошибок. Новый живой повтор ещё требуется.

На кандидате `0dfafd2` F01/F02 снова создали верные проекты (8.629/9.616 с),
но F04 вернул два JSON-объекта с посторонним текстом между ними. Строгий парсер
отклонил ответ; ход и расходы сохранены. Добавлен отключённый по умолчанию
`PARTNER_MODEL_JSON_OUTPUT`: Chat Completions использует response_format=json_object,
Responses — text.format=json_object; настройка записывается в тарифный снимок.
Маршрут Polza/openai для Luna объявляет response_format в публичном каталоге.
JSON-режим не заменяет проверку ссылок, прав и инженерных условий и не добавляет
скрытых повторных вызовов. См. [контракт Polza](https://polza.ai/docs/gaidy/structured-output.md).

На первом повторе с JSON-режимом формат прочитан корректно, но F02 дал два
подтверждённых правила вместо трёх: модель ошибочно задала NTP как two-way.
Решатель сохранил NTP неизвестным и не включил неверное правило в подтверждённый
минимум. В инструкцию явно перенесено общее правило методики 1.9: NTP —
однонаправленный UDP внутрь защищённой сети, с объединением получателей времени.
Это правило для протокола, не подстановка ответа по номеру сценария.
