# Совместная разработка

## Ветки

- `main` — проверенные выпуски через PR из `develop`. Публикацию образов,
  релиз и тег `vX.Y.Z` согласовать с капитаном.
- `develop` — рабочая интеграционная ветка. Изменения продукта входят через PR.
- Рабочие ветки начинать от актуальной `origin/develop`. Использовать
  `feature/*`, `fix/*`, `chore/*` и другие префиксы по назначению,
  строчные буквы и дефисы. Имя описывает задачу.
- Ветки `checkpoint/*` фиксируют состояние для показа. Продолжение разработки
  ведётся в `develop` и рабочих ветках.

## Объявление задачи

1. Выполнить `git fetch origin --prune`. Проверить свежие коммиты
   `origin/develop`, записи в `progress.md`, открытые PR и изменения в
   активных ветках, включая ветки без PR. При пересечении согласовать границы
   либо взять свободную задачу.
2. Обновить локальную `develop` fast-forward. **Перед созданием рабочей ветки**
   внести в `progress.md` название задачи, её границы и ответственное лицо.
   Формат отметки — «Задача уже занята и сейчас реализуется by Fazbear.»
   Для других участников указать имя ответственного.
3. Сделать один короткий коммит с названием задачи прямо в `develop` и
   **сразу отправить его в `origin/develop`**. Если удалённая ветка продвинулась,
   перечитать новые изменения и ещё раз проверить доступность задачи перед
   повторной отправкой. Создать рабочую ветку после подтверждения публикации.
4. Для изменения границ обновить отметку и описание PR. По завершении
   отметить результат в `progress.md` в составе PR.

## Синхронизация и PR

- Повторять fetch и просмотр открытых PR после перерыва, перед публикацией
  и перед слиянием. Сначала изучить новые коммиты `develop`, затем влить
  `origin/develop` в рабочую ветку и повторить затронутые проверки.
- Делать короткие предметные коммиты на проверяемых стадиях. Изменения схем,
  миграций и общих интерфейсов указывать в PR. Описание PR содержит фактические
  изменения, выполненные проверки и известные ограничения.
- Перед merge проверить diff и SHA проверенной версии. В `develop` учитывать
  доступные локальные проверки и фиксировать состояние CI. Для `main`
  обязательны зелёные проверки PostgreSQL, контейнеров, браузера, конвертации
  и восстановления на версии, которую выпускают.
- После подтверждённого merge обновить локальную `develop` fast-forward.
  Удалить завершённую рабочую ветку на `origin`, сверив её вершину с влитым PR.
  Локальную завершённую ветку удалять обычной командой `git branch -d`.
  Сохранять ветки с незавершённой работой. Опубликованную историю не
  переписывать и force push не использовать.

## Проверки и материалы

- Базовая проверка — `./init.sh check`. Рабочие команды запуска см. в README.
  Для интеграций использовать отдельную PostgreSQL. Тесты Garage и Qdrant
  помечать `storage`, реальные запуски конвертера — `parser`.
- Сверять права на владельца, фрагменты, вложения и скачивание оригинала
  до выдачи материала. Администрирование не даёт доступа к чужим документам.
- Для проверки использовать синтетические материалы и локальные подключения.
  Платные вызовы согласовываются отдельно.
- Секреты, локальные окружения, переписки, закрытые материалы, кэши и сборки
  хранить вне отслеживаемого дерева. Сохранять обязательные лицензии.
